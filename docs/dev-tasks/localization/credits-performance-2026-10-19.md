# 片尾主线程停顿定位

状态：已定位并修复，1.5.15已通过安装器安装。见[候选核验](../../../runtime/evidence/credits-performance-verification-2026-10-19.json)及[安装核验](../../../runtime/evidence/credits-performance-install-verification-2026-10-19.json)。

## 定位结果

真实原游戏credits资产经过原格式器输出111,095字符、4,814个富文本标签、2,495行。独立CLI调用现有离线规则消费者，热路径约5.6–6.1毫秒；完整正文没有整段译文命中。这排除了“词表正则查询本身每次需要半秒”的猜测。

[深度CPU采样](../../../runtime/evidence/credits-performance-deep-2026-10-19.json)从真实`Boss.ActivateCredits`进入片尾，在正文设置时记录到`TranslationToggle.PrepareOfflineText → AutoTranslationPlugin.TryTranslate`约817毫秒，其中`TranslateByParserResult`约523毫秒、`RichTextParser.Parse`约279毫秒。同一份正文又在后续`WaitForTextStablization.MoveNext`中处理一次，约633毫秒；其中`TranslateOrQueueWebJobImmediateByParserResult`约533毫秒，对应自然帧间隔约649毫秒。耗时为嵌套包含关系，不能相加。该帧GC计数未变，托管内存增长约83MB。

富文本解析器最多拆出2,945个片段，生成3,788,928条前后文引用。本机XUnity源码为每个片段遍历其前后所有片段收集上下文，存在二次复杂度；片段翻译和拼接另有显著成本，不能将整段停顿全部归因于单一循环。处理发生在Unity主线程，因此圆环和场景更新都会等待；圆环绘制本身不是本轮所抓慢帧的来源。

中文与F8原文显示模式均出现，原因是本项目在两种模式下都预登记离线组合缓存，XUnity也仍有文字稳定检测。原文显示模式不等于禁用补丁的原版基线。上述是隔离副本真实CPU调用、后台主动刷新Canvas的采样，不是玩家现场录屏、GPU验收或退出阶段所有卡顿的证明；可以解释进入名单后停顿，不能断言玩家上次退出的每次停顿均来自同一调用。

早期三份探索报告的runner记录`target_frame_rate=10`只是初始化请求值；原片尾Start会改成60，探索时未持续强制10FPS。其CPU栈定位仍可参考，但不能称全程10FPS。后续对照探针在片尾Start后重新限制10FPS，并逐帧记录目标值，不改垂直同步等原生显示设置。

## 修复范围

只将真实`CreditsPlayer.TextField`登记为名单正文，调用XUnity的组件忽略接口，并跳过本项目对该组件的组合缓存预解析；名单依然接收原游戏原文。不能按长度、层级名称或富文本类型泛化排除其它正文。右下角提示继续正常翻译、F8与白字显示，原空格快进、音乐、结局条件及Ctrl手势保留。

首次仅登记忽略组件的候选已去掉同步解析，但[实测](../../../runtime/evidence/credits-performance-candidate10-2026-10-19.json)延迟任务仍耗时634毫秒：TMP启用时已经排队，XUnity的稳定回调不会复核`ShouldIgnore`。最终修复在真实组件稳定协程的`MoveNext`恢复前检查名单登记，取消该正文已排队任务并复位稳定状态；其它组件和全局文字稳定协程原样运行。直接挂钩真实`MoveNext`，不依赖可能被Mono内联的迭代器工厂。

销毁跳过组件时释放正文登记；若正文组件仍存活，恢复其自动翻译许可。名单全文哈希、F8前后逐字一致性和提示翻译在真实隔离运行中验证。

前三次新对照在进入正式采样前触发窗口保护，进程已终止，原8存档哈希、时间及数量未变，临时副本已清理；失败证据保持失败，未计入性能结论。关闭设置页的最初猜测没有得到复验支持，已撤回相关探针改动。移除新采样器的`QualitySettings.vSyncCount`赋值后同条件复验通过；测试只限制目标帧率，不改变其它原生显示参数。
